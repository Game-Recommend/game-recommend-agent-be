# 취향 적합도 평가

에이전트가 **통과 후보 중 무엇을 골랐는지**가 질문에 맞는지를 보는 평가다. 문항은
[questions.md](questions.md), 실행 데이터는 [dataset.json](dataset.json), 원시 기록은 [runs/](runs)에 있다.

엔드투엔드 평가(`evals/agent_e2e/`)는 조건 준수·단계 실행·답변 형식을 보고 추천의 질은 재지 않는다.
그 평가셋은 100문항 중 60문항이 검색 조건이 없거나 장르·플랫폼 하나뿐이고 취향이 뽑히는 문항이 6개라,
무엇을 고르든 맞고 틀림을 가릴 기준이 없다. 에이전트가 통과 후보 중 질문과 취향에 맞는 게임을 고르게
한 변경(`AGENT_SYSTEM`의 Candidate Verification)은 그 평가로는 측정되지 않는다.

**실제 외부 API와 LLM을 부른다.** 40문항에 에이전트 약 $0.3, 심판 약 $0.03, 10분 안팎이다. CI에서는
돌리지 않는다.

## 무엇과 비교하는가

정답 추천 목록은 없다. 대신 같은 실행 안에서 두 목록을 만든다.

| 목록 | 만드는 법 |
| --- | --- |
| 에이전트 | 에이전트가 실제로 추천한 게임 |
| 대조 | 같은 조건으로 검색·가격·사양을 다시 돌려, **판정을 통과한 후보를 검색 순서(인기순)대로** 같은 개수만큼 자른 것 |

대조 목록은 고정 파이프라인이 했을 선택이다. 두 목록은 같은 후보 풀과 같은 판정에서 나오므로 검색
품질, 도구 유무, 빈 추천의 영향을 받지 않는다. 남는 차이는 **무엇을 고를지를 LLM에 맡긴 효과**뿐이다.
원본 저장소(`game-recommend-be`)를 돌릴 필요가 없고, 검색 수정이 원본에 없다는 점도 상관이 없다.

## 심판

[judge.py](judge.py)의 LLM 심판(`gpt-4o-mini`)이 두 목록 중 질문에 더 맞는 쪽을 고른다.

- **절대 점수가 아니라 1:1 비교다.** 1~5점 채점은 같은 코드로도 실행마다 0.1~0.3씩 흔들렸다
  (`evals/agent_e2e/REPORT.md`). 같은 질문의 두 목록을 나란히 놓고 고르게 한다.
- **어느 쪽이 에이전트인지 알리지 않고, 자리(A/B)를 바꿔 두 번 묻는다.** 두 번 모두 같은 쪽을 골라야
  그쪽의 승리다. 엇갈리면 자리 편향으로 보고 비김으로 센다.
- 근거는 IGDB와 가격 Tool이 돌려준 값(분류, 소개 300자, 완료 시간, 가격)뿐이다. 두 목록의 게임은
  같은 방식으로 적힌다.
- 두 목록이 같은 게임이면 심판을 부르지 않는다(`same`).

| 결과 | 뜻 |
| --- | --- |
| `agent` / `baseline` | 자리를 바꿔도 같은 쪽이 이겼다 |
| `tie` | 심판이 비겼다고 했거나 자리를 바꾸자 판정이 엇갈렸다 |
| `same` | 에이전트가 인기순 그대로 골랐다. 고를 여지가 없었거나 고르지 않았다 |
| `empty` | 에이전트가 추천을 내지 않았다 |

`summary.json`의 `agent_win_rate`는 승부가 난 문항(`agent` + `baseline`) 중 에이전트가 이긴 비율이다.
0.5면 LLM에 맡긴 선택이 인기순보다 나을 것이 없다는 뜻이다. `changed_rate`(목록이 달랐던 비율)와 함께
읽는다.

## 문항에 넣지 않은 것

- **사양 조건.** GPU·CPU 판정은 LLM이 하므로 대조 목록을 다시 계산할 때 판정이 달라질 수 있다.
- **평점 기준**("Steam 평가 좋은"). 리뷰 점수 Tool은 에이전트 쪽에만 있어, 넣으면 선택이 아니라 도구
  유무를 재게 된다.
- **무료 강제·아주 낮은 예산.** 후보가 전부 탈락해 비교할 목록이 없다.
- **제외 표현**("공포 빼고"). 질문 분해가 흔들리는 자리라 선택이 아니라 파서를 재게 된다.

## 실행

저장소 루트에서 실행한다. `.env`의 키를 읽는다.

```bash
.venv/bin/python -m evals.relevance.run_eval --limit 5      # 먼저 작게 확인한다
.venv/bin/python -m evals.relevance.run_eval                # 40문항, 동시성 2
.venv/bin/python -m evals.relevance.run_eval --no-judge     # 목록이 달라지는지만 본다(심판 생략)
.venv/bin/python -m evals.relevance.run_eval --judge-model gpt-4o

.venv/bin/python evals/relevance/build_dataset.py            # 문항 재생성
.venv/bin/python -m pytest -q evals/relevance/test_relevance.py
```

기록은 `runs/<UTC timestamp>/`에 남는다. `results.jsonl`에 문항별 두 목록·겹침·두 번의 판정과 사유,
`summary.json`에 집계, `metadata.json`에 모델과 데이터·프롬프트 SHA-256이 들어간다. 키는 기록하지 않는다.

## 읽을 때 주의

- **심판도 틀린다.** 사람이 공인한 정답이 아니다. 같은 후보 풀에서 나온 두 목록의 상대 비교로만 읽는다.
- 40문항은 적다. 승 12 대 패 8 같은 차이는 우연일 수 있다. 같은 실행을 두세 번 반복해 흔들림을 본다.
- 심판은 질문에 맞는 정도만 본다. 한 시리즈로 채운 목록을 따로 감점하지 않는다.
- 대조 목록은 에이전트 실행 직후에 다시 검색해 만든다. 에이전트가 추천한 게임이 그 후보에 없으면
  `pool_mismatch`에 남는다. 이 값이 0이 아니면 두 목록의 후보 풀이 달랐던 것이다.
- 에이전트의 선택은 LLM이 하므로 같은 질문에도 실행마다 목록이 달라진다.
