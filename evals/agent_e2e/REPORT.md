## 발견 1. 질문 절반이 추천 0개로 끝난다

50문항이 `모든 필수 조건을 충족한다고 확인된 후보가 없습니다` 경고와 함께 빈 목록을 냈다.
경고를 내는 동작 자체는 옳다(계약대로다). 문제는 빈도이고, 원인은 두 겹이다.

### 1-1. 후보가 한국 스토어에서 팔지 않는 고전 게임이다

`"게임 1개만 추천해줘"`를 따로 실행해 제외된 후보의 판정을 들여다봤다.

```
후보 30개 → 판정한 5개가 전부 탈락
  Max Payne                  : 가격 unmet (한국 스토어 미판매)
  X-COM: UFO Defense         : 가격 unmet (한국 스토어 미판매)
  X-COM: Terror From the Deep: 가격 unmet (한국 스토어 미판매)
```

`"3만 원 이하"` 쪽도 같다. 제외 16건의 가격 판정이 `unknown` 11건(원화 가격 확인 불가),
`unmet` 5건(미판매)이다. 후보로 올라온 이름이 Thief(1998), Baldur's Gate(1998),
Jagged Alliance(1995), Max Payne(2001)처럼 1990~2000년대 작품에 쏠려 있다.

즉 **IGDB 검색이 내놓는 후보 자체가 한국 Steam에서 구매 가능한 게임이 아니다.** 조건이 느슨한
질문(`count` 계열은 개수만 말한다)일수록 이 쏠림이 심해, `count` 80%·`tight` 100%가 빈 추천으로
끝났다. 반대로 `budget` 계열은 20문항 전부 추천을 냈는데, 예산이라는 조건이 붙으면서 후보 구성이
달라진 것으로 보인다. 검색 인자를 무엇으로 정렬·필터하는지는 이 평가셋의 범위를 넘고,
IGDB 담당 모듈(`app/tools/game_search.py`, `app/clients/igdb.py`)에서 볼 문제다.

### 1-2. 에이전트가 후보를 일부만 판정하고 포기한다

> **정정 (2026-09-19).** 이 절의 진단은 틀렸다. `excluded_ids`는 "조회했고 **조건에 걸린** 후보"라서
> 아래 표의 수는 판정한 후보 수가 아니라 **탈락한 후보 수**다. 에이전트는 후보 전체를 조회했고,
> 통과한 후보를 두고도 빈 목록을 냈다. 근거와 수정은
> [맨 아래 절](#빈-추천의-원인-정정과-되묻기-2026-09-19)에 있다. 아래 본문은 당시 기록으로 남긴다.

빈 추천 50건의 **제외 후보 수**를 세면 이렇다. `excluded_ids`는 "조회했는데 조건에 걸린 후보"이고
조회하지 않은 후보는 세지 않으므로(`app/agent/context.py`), 이 수가 실제로 판정한 후보 수다.

| 판정한 후보 수 | 문항 수 |
| --- | --- |
| 30개 (전부) | 16 |
| 17개 | 3 |
| 9~24개 | 7 |
| 5개 | 8 |
| 1~4개 | 11 |
| **0개** | **5** |

**빈 추천 50건 중 34건은 후보 30개 중 일부만 판정하고 포기했다.** 5건은 아무것도 조회하지 않고
"조건에 맞는 게임이 없다"고 답했다. 도구 호출 횟수를 보면 빈 추천 50건 중 45건이 `도구 호출 3회`다.
`search_games` 한 번, `get_prices`·`assess_hardware` 한 번씩 부르고 끝냈다는 뜻이다.
남은 후보로 두 번째 판정을 돌린 경우가 거의 없다.

러너의 안전망(`_ensure_checks`)은 **에이전트가 추천하기로 정한 게임**의 미조회 항목만 채운다.
후보를 더 보게 만들지는 않는다. 그래서 처음 고른 표본이 전멸하면 그대로 빈 목록이 된다.

같은 질문 `"게임 1개만 추천해줘"`가 평가 실행(E031)에서는 0개, 따로 실행했을 때는 1개를 냈다.
어느 후보를 표본으로 고르느냐에 결과가 달려 있다.

## 발견 2. 답변 문단이 추천 목록과 어긋난다 — 19문항

`answer_format` 실패 50건의 내역은 문장 수 31건, **게임 이름 누락 19건**이다. 뒤쪽이 실제 결함이다.

스모크 실행에서 처음 잡힌 형태가 전형적이다.

```
추천 목록: Thief II: The Metal Age, Thief: Deadly Shadows, Thief,
          Jagged Alliance, Jagged Alliance 2
답변 문단: ... 'Jagged Alliance'는 저렴한 4,090원에 구매할 수 있으며,
          'Jagged Alliance: Deadly Games'는 같은 가격입니다.
```

추천 목록에 있는 `Jagged Alliance 2`가 답변에 없고, 목록에 없는
`Jagged Alliance: Deadly Games`가 답변에 등장한다. 사용자는 카드에서 `Jagged Alliance 2`를
보면서 본문에서는 다른 게임 이름을 읽는다. 이름이 비슷한 시리즈물에서 잘 나타난다.

LLM 심판이 이 문항에 `grounded=3`을 주고 사유로 정확히 같은 지적을 했다. 코드 검사와 심판이
독립적으로 같은 결함을 가리켰다. 심판의 `grounded` 4점 미만 19문항은 게임 이름 누락 19건과
문항 수가 같다.

## 발견 3. 제외 조건이 검색에 전달되지 않는다 — E058

```
질문: 공포 빼고 3만 원 이하 게임 알려줘
추천: Vampire: The Masquerade - Bloodlines, Vampire: The Masquerade - Redemption,
      BioShock, Dungeon Keeper 2, Dead Space 2
```

추천된 5개 전부의 IGDB 장르·테마에 `Horror`가 있다. 제외 요청이 추천에 전혀 반영되지 않았다.

파서는 `excluded_genres`를 뽑지만, 그 값을 `search_games` 인자로 넘기는 것은 **에이전트의 판단**
이다(`app/agent/tools/search.py`의 `SearchGamesArgs.excluded_genres`). 러너의 후검증은 가격·사양만
보고 제외 장르는 보지 않으므로, 에이전트가 빠뜨리면 걸러지지 않는다. `exclude` 계열 15문항 중
추천을 낸 4문항에서 1건이 이 형태다.

## 발견 4. 사양을 말했는데 판정을 건너뛴 게임이 추천된다 — E081

루트 README의 예상 질문(하드웨어)이다.

```
질문: 내 노트북이 i5-1240P, RAM 16GB, 내장그래픽인데 원활하게 할 수 있는 게임 중에서
      평점 좋은 게임 추천해줘.
추천: Thief II: The Metal Age (사양 판정 skipped)
      Vampire: The Masquerade - Redemption (사양 판정 skipped)
```

사용자가 CPU·RAM·그래픽을 말했는데 사양 판정이 `skipped`다. `skipped`는 판정을 하지 않았다는
뜻이고, 러너의 후검증은 `met`과 `skipped`를 모두 통과로 본다. 그래서 "원활하게 할 수 있는"이라는
요청에 사양을 확인하지 않은 게임이 올라간다.

이 질문은 `evals/parser_conditions/`의 Q181과 같은 질문이고, 거기서는 파서가
`hardware.gpu="내장그래픽"`을 넣는 것이 문제였다. 두 평가셋이 같은 질문의 다른 층을 가리킨다.

## 발견 5. 빈 추천일 때 답변 길이 계약이 없다 — 29문항

`answer_format`의 문장 수 실패 31건 중 29건이 추천 0개인 문항이다. 추천이 있는 문항의 문장 수
분포는 `{3:14, 4:13, 5:9, 6:12, 2:2}`로 대체로 계약(3~6문장)을 지키는데, 빈 추천 쪽은
`{2:27, 3:20, 1:2, 4:1}`로 2문장에 몰린다.

`app/agent/schemas.py`의 `RecommendationDraft.answer` 설명은 조건 없이 "한국어 3~6문장"을
요구한다. 추천할 게임이 없을 때 3문장을 채우라는 것이 타당한지는 계약이 답하지 않는다.
**이 29건은 에이전트의 결함이라기보다 계약의 공백이다.** 빈 결과의 답변 길이를 따로 정하면
채점기도 함께 고쳐야 한다.

추천이 있는데 2문장인 2건은 계약 위반이다.

## 단계 실패 2건

`trajectory` 실패 2건(E047, E085)은 `가격`·`하드웨어` 단계가 `failed`로 끝난 경우다. 외부 API
호출 실패로 보이고, 두 문항 모두 추천은 냈다. 실패한 단계가 있었다는 사실이 최종 응답의
경고에는 드러나지 않는다.

## 실행 환경에 대한 기록

처음에 동시성 4로 돌렸을 때 **100건 중 50건이 연결 오류**로 끝났다. 45건이 질문 분해 단계의
OpenAI 연결 오류, 5건이 에이전트 루프의 연결 오류였고 LangSmith 전송도 DNS 해석에 실패했다.
한 질문이 IGDB·Steam·CheapShark·환율·OpenAI를 여러 번 부르므로 동시성 4는 로컬 네트워크에
과했다. 동시성 2로 낮춰 다시 돌린 것이 이 보고서의 실측이고 오류 0건이다.

이 경험에 따라 채점기는 **오류로 끝난 문항을 정확도 분모에서 뺀다**(`evals/price_hardware`와 같은
관례). 실행 환경 문제가 에이전트 품질 수치로 섞이지 않게 하려는 것이다.

### 에이전트가 이긴 것 — 답변 형식과 근거

| 답변 형식 위반 | 원본 | 에이전트 |

마크다운 위반이 17건 → 0건이다. 이 저장소는 최종 출력을 `ToolStrategy(RecommendationDraft)`로
받아 모델이 자유 텍스트로 끝내지 못한다. 형식 계약을 코드로 강제한 효과로 보인다.

LLM 심판의 근거 점수도 3.54 → 4.27로 올랐다. 답변이 Tool 결과에서 덜 벗어난다는 뜻이다.

**게임 이름 누락 19건은 양쪽이 똑같다.** 전환과 무관한 최종 답변 LLM의 공통 결함이다
(발견 2 참고). 이름이 비슷한 시리즈물에서 목록과 본문이 어긋난다.

### 에이전트가 잃은 것 — 추천 0개가 19건 → 50건

> **정정 (2026-09-19).** 아래의 "표본이 전멸하면 포기한다"는 설명은 틀렸다. 구조의 대가가 아니라
> 빈 초안을 그대로 받아 준 러너의 공백이었고, 고쳤다.
> [맨 아래 절](#빈-추천의-원인-정정과-되묻기-2026-09-19) 참고.

전환의 대가가 여기서 드러난다. 원본 고정 파이프라인은 검색한 후보를 순서대로 다 훑는다.
에이전트는 **LLM이 판정할 후보를 고르고, 그 표본이 전멸하면 포기한다.** 발견 1-2에 적은
"빈 추천 50건 중 34건이 후보 30개 중 일부만 판정하고 포기"가 원본과 비교하니 구조의 차이로
확인된다.

지연도 원본이 조금 빠르다(11.6초 vs 12.2초). Tool 선택에 LLM 턴이 더 들어가기 때문이다.

발견 1-1(후보가 한국 스토어 미판매 고전 게임에 쏠림)은 양쪽 공통이다. IGDB 클라이언트와 검색
도구가 두 저장소에서 같은 코드다. 다만 원본 `.env`의 IGDB 자격이 다르므로(`IGDB_CLIENT_ID`가
서로 다른 앱) 후보 구성 차이에 그 영향이 섞여 있을 수 있다. 그래서 추천 목록 자체는 비교하지
않고 축별 통과 수와 위반 유형만 비교했다.

### 조건·궤적은 거의 같다

조건 위반은 양쪽 2건씩이고 형태도 비슷하다. 제외 요청한 장르가 추천에 섞인 경우다
(원본은 `Fallout: New Vegas` 등에 Shooter, 에이전트는 `Dead Space 2` 등에 Horror).
제외 조건을 검색에 넘기는 일은 원본에서는 고정 파이프라인이, 이 저장소에서는 LLM이 하는데
**둘 다 같은 빈도로 빠뜨린다.**

궤적은 원본 96, 에이전트 98이다. 원본은 질문에 필요한 단계를 완료하지 못한 경우가 4건,
에이전트는 단계가 실패로 끝난 경우가 2건이다.

## 읽을 때 주의

- **한 번의 측정이다.** 에이전트의 Tool 선택은 LLM이 하고 IGDB·Steam 데이터는 시간에 따라
  바뀐다. 같은 질문이 실행마다 다른 게임을 내는 것은 정상이다. 발견 1-2에 적었듯 같은 질문이
  0개와 1개를 오갔다.
- 회귀 비교는 축별 통과 수와 위반 유형으로 한다. 추천 목록을 직접 비교하지 않는다.
- `constraints` 98/100은 빈 추천 50건이 끌어올린 수치다. 추천을 낸 50문항만 보면 48/50이다.
- LLM 심판 점수는 사람이 공인한 정답이 아니다. 자동 정확도에 섞지 않았다.
- 발견 1-1(후보 쏠림)은 이 평가셋이 원인을 규명할 수 있는 범위를 넘는다. IGDB 검색 인자와
  정렬을 보는 별도 평가가 필요하다.
- 모델 alias의 서버측 버전을 고정하지 않았다.

## 채점 기준 변경 (2026-09-18)

발견 5의 결론("에이전트의 결함이라기보다 계약의 공백")을 채점기에 반영했다. **추천이 0개면 답변
2~6문장을 받는다.** 추천이 있으면 그대로 3~6문장이고, 1문장은 이유가 빠진 것이라 여전히 위반이다.

## 빈 추천의 원인 정정과 되묻기 (2026-09-19)

### 발견 1-2의 진단은 틀렸다

발견 1-2는 빈 추천의 `excluded_games` 수를 "판정한 후보 수"로 읽고, 에이전트가 후보 일부만 판정하고
포기한다고 결론 냈다. `CandidateStore.excluded_ids()`는 **조회했고 조건에 걸린 후보**만 돌려준다.
조회했는데 통과한 후보는 추천도 제외도 아니어서 어디에도 세지지 않는다. 그 표의 수는 탈락한 후보 수였다.

같은 문항을 원본과 나란히 놓으면 드러난다.

```
질문: 게임 2개 추천해줘 (E032)
원본     질문 분해 → 게임 검색(후보 30개) → 하드웨어 → 가격 → 조건 판정(통과 25개 중 2개 선택, 제외 5개)
에이전트 질문 분해 → 게임 검색(후보 30개) → 하드웨어 → 가격 → 조건 판정(추천 0개, 제외 5개)
```

제외 5개가 같다. 에이전트도 30개를 다 조회했고(`AGENT_SYSTEM`이 후보 전체를 한 번에 넘기라고 시킨다)
같은 5개가 한국 스토어 미판매로 탈락했다. 에이전트를 따로 돌려 후보 저장소를 들여다본 결과다.

```
후보 30 | 가격 조회 30 {skipped 25, unmet 5} | 사양 조회 30 {skipped 30}
조회한 후보 30개 중 통과 25개 | 에이전트가 추천한 수 0
답변: 조건에 맞는 추천 가능한 게임을 찾지 못했습니다. 확인된 후보 게임이 없으므로 추천할 수 있는
      게임이 없습니다.
```

**모델이 `status=skipped`(사용자가 그 조건을 말하지 않음)를 "확인하지 못했다"로 읽고 통과 후보 25개를
두고 빈 목록을 냈다.** `build_user_input`이 "skipped를 실패나 조건 미충족으로 처리하지 마세요"라고 이미
지시하는데도 그랬다. 그리고 `CandidateStore.validate_draft()`는 빈 초안을 무조건 통과시켰다. 예산도
사양도 말하지 않은 질문일수록 전부 `skipped`라서 `count`(개수만 말한다) 계열이 가장 크게 무너졌다.

따라서 "에이전트가 잃은 것" 절의 해석(LLM이 표본을 고르고 전멸하면 포기하는 구조의 대가)도 틀렸다.
구조가 아니라 러너의 공백이었다.

### 빈 추천이 전체 수치를 끌어올렸다

빈 추천은 세 축을 거의 자동으로 통과하고, LLM 심판이 만점을 주고(지어낼 것이 없다), 빨리 끝난다.
빈 추천이 19건에서 47~50건으로 늘면서 전체 통과율·심판 평균·지연이 함께 좋아 보였다.

  (리뷰 요약 순차 실행, 중앙값 5.96초).

### 수정

- **러너의 빈 초안 되묻기** (`app/agent/runner.py`). 빈 초안인데 판정을 통과한 후보가 있으면 통과 후보
  목록과 `skipped`의 뜻을 붙여 한 번만 되묻는다(`build_empty_challenge`). 거부 재시도 횟수를 쓰지 않고,
  다시 비어 있으면 에이전트의 판단으로 받는다. 되물은 뒤의 초안이 끝내 후검증을 통과하지 못하면 502가
  아니라 처음의 빈 초안으로 응답한다. 통과 후보가 없는 빈 초안(무료 강제 등)은 되묻지 않는다.
- **채점기** (`score.py`, `run_eval.py`). `조건 판정` 단계가 남기는 `통과 N개`를 읽어, 통과 후보가 있는데
  추천이 0개면 `constraints` 위반으로 센다. 요약은 추천을 낸 문항만의 수치(`with_recommendations`)와
  통과 후보가 있었던 빈 추천 수(`overlooked_empty`)를 함께 낸다.

- **에이전트의 우세가 빈 추천과 무관하게 처음 확인됐다.** 추천을 낸 문항 수는 원본과 같아졌고(81 vs 78~80),
  그중 세 축을 통과한 문항은 원본 29, 에이전트 53~55다. 세 실행 사이의 흔들림(2)보다 차이(24~26)가 크다.
  차이는 답변 형식에서 나온다(추천을 낸 문항의 형식 통과 31/81 vs 56~59/78~80). 조건 축은 비슷하다.
- **전체 통과 수가 80 → 71~75로 내려간 것은 나빠진 것이 아니다.** 자동으로 통과하던 빈 추천 27~28건이
  실제 추천이 되면서 형식·조건 검사를 받게 됐다. 측정 대상이 돌아온 것이다.
- **빈 추천이 가리던 결함이 드러난다.** 2차의 E079는 파서가 "3000원 이하"를 `max_price_krw=30000`으로
  뽑아 3천 원을 넘는 게임 5개를 추천했다(수정 전에는 빈 추천이라 조건 축을 통과했다). 1차·3차의 E081은
  사양 판정이 `skipped`인 게임을 추천했다(발견 4 그대로다).
- **원본이 빈손인데 에이전트가 추천을 낸 문항**이 1~2개 생겼다(E063, E081). E063(`GTX 1650, RAM 8GB 노트북`)은
  세 실행 모두 조건 위반 없이 4~5개를 추천했고, E081은 위의 조건 위반이다.
- **지연.** 되묻기는 LLM 턴을 하나 더 쓴다. 수정 전에 빈손으로 끝나던 문항(중앙값 7.57초)이 추천을 내면서
  9.9~10.6초가 됐다. 추천을 낸 문항 전체의 중앙값은 10.7~11.1초로 수정 전(11.8초)보다 늘지 않았는데, 새로
  추천을 내는 문항이 조건이 단순해 빨리 끝나는 문항이기 때문이다. 도구 호출 수 분포는 그대로다
  (84~88문항이 도구 호출 3회).

### 되묻기 메시지의 문구

세 실행은 문구를 고치며 잰 것이다. "수정 전에 빈손이었다가 이번에 추천을 낸 문항"(27~28개)을 되묻기를
거친 답변으로 보고 나머지(51~52개)와 나눠 봤다.

| --- | --- | --- | --- |
| 문구 | 통과 후보 목록, "skipped는 통과", 빈 목록 출구 | + "3~6문장, 이름 모두, 사양 판정 등으로 확인된 이유" | "skipped는 검사하지 않은 것, 추천을 막는 사유가 아님" + "skipped인 조건을 충족·확인했다고 쓰지 말 것" |

- 1차 문구는 답변 형식을 말하지 않아 게임 이름만 나열한 2문장 답변이 나왔다.
- 2차 문구는 "skipped는 통과"와 "사양 판정으로 확인된 이유를 쓰라"가 겹쳐, 되물은 답변의 1/3이
  "사양도 충족합니다"처럼 **검사하지 않은 조건을 충족했다고 썼다.** 최종 문구에서 1건으로 줄었다.
- **되물은 답변은 어느 문구에서도 심판 근거 점수가 낮다**(2.5~3.1 vs 나머지 3.4~3.6). 되묻기 턴에서 Tool을
  금지해 리뷰 요약 없이 답변을 쓰기 때문이고(카드의 리뷰 요약은 러너가 뒤에 채운다), 모델이 빈자리를
  일반적인 게임 설명으로 메운다. 되묻기 턴에 `summarize_reviews`만 허용하는 것이 다음에 볼 자리다.
  지연과 호출 반복 위험이 함께 늘어나므로 재고 정해야 한다.

### 오류 3건

1차 1건(E025), 3차 2건(E043, E086)은 분모에서 뺐다. 셋 다 되묻기 이전의 실패 경로다.

- E025·E043은 첫 에이전트 루프에서 초안을 내기 전에 `get_prices`(·`assess_hardware`)를 1초 간격으로
  약 10번 반복하다 반복 상한(`GraphRecursionError`)에 걸렸다. 2차의 E043은 같은 반복을 14회 하고 추천을 냈다.
- E086은 추천 개수 초과(3개 요청에 6개)로 두 번 거부돼 502가 됐다. 되물은 뒤였다면 빈 초안으로
  돌아갔을 경로다.
- 09-17·18의 세 실행에는 반복 상한 오류가 없었다. 이날은 CheapShark 폴백 가격 조회가 실행 내내 HTTP 오류로
  실패했고(`Fallback price lookup failed`), 가격 결과가 비는 후보 때문에 모델이 재호출을 반복했을 가능성이
  있다. 원인은 확인하지 못했다.

### 남은 것

- 전후 비교 차트(`docs/eval_comparison.*`)와 루트 README의 비교 표는 수정 전 수치다.
  → 2026-09-20에 갱신했다([전후 비교 갱신](#전후-비교-갱신과-채점기-동기화-2026-09-20)).
- 평가 코드는 두 저장소에 같은 내용으로 두는 것이 원칙인데, 이번 채점기 변경은 아직 원본 저장소에
  옮기지 않았다. 원본 기록은 `통과 N개`를 이미 남기므로 옮기면 그대로 채점된다(원본의 빈 추천 19건은
  통과 후보 0개 16건, 검색 결과 없음 3건이라 새 규칙에 걸리지 않는다).
  → 2026-09-20에 옮겼다(같은 절).
- 지연 비교는 여전히 공정하지 않다. 리뷰 요약 병렬화 등 I/O 패치가 원본 저장소에는 없다.

## 검색 후보 풀 교체와 가드 두 개 (2026-09-19)

발견 1-1(후보가 1990~2000년대 게임에 쏠린다)의 원인은 검색 쿼리의 `sort id asc`였다. IGDB id는 등록
순서라 질문과 무관하게 id 1번 Thief II부터 나왔다. 검색만 따로 잰 기록과 원인 분석은
[evals/search_pool/REPORT.md](../search_pool/REPORT.md)에 있다. 이 절은 검색을 고친 뒤의 엔드투엔드 결과다.

### 바꾼 것

1. **검색** (`app/clients/igdb.py`). 많이 평가된 순 정렬, 본편·리메이크·리마스터만, 플랫폼을 말하지
   않으면 PC. 분류어가 IGDB 장르·테마에 없으면 게임 모드·키워드로 찾고, `play_mode`와 `connection`을
   검색에 쓴다.
2. **선택 기준** (`AGENT_SYSTEM`). 통과 후보가 요청 개수보다 많으면 검색 순서(인기순)를 보존하는 대신
   질문과 취향에 맞는 순으로 고르고, 한 시리즈로 목록을 채우지 않는다.
3. **id 가드** (`get_prices`, `assess_hardware`). LLM이 넘긴 id와 무관하게 검색된 후보 전체를 조회한다.
4. **이름 되묻기** (`runner.py`). 추천한 게임 이름이 답변에 없으면 빠진 이름과 추천 목록을 붙여 한 번
   되묻는다. 빈 초안 되묻기와 같은 틀이고, 다시 어긋나면 그대로 받는다.

3과 4는 계획에 없던 것이다. 1·2만 넣고 재자 통과 수가 75 → 53으로 떨어졌고, 원인을 기록에서 찾아 넣었다.

### 검색만 바꾸면 나빠진 이유

후보가 Thief II(id 1)에서 Red Dead Redemption 2(id 25076), Elden Ring(id 119133)으로 바뀌자 **모델이
id를 옮겨 적다 틀렸다.** 프롬프트는 `get_prices`·`assess_hardware`에 후보 30개의 id를 모두 넘기라고
했는데, 따로 돌려 보면 30개 중 10~26개만 넘겼고 없는 id를 섞기도 했다.

- 조회하지 않은 후보는 추천될 수 없다. "만 원 이하 게임"에서 10개만 조회하고 그중에 없자 빈 추천을 냈다.
- 없는 id가 섞이면 Tool이 호출 전체를 거부한다. 100문항 중 8~9문항에서 가격·하드웨어가 동시에 실패한 뒤
  다시 호출됐고(궤적 축 97 → 90), 재호출이 반복 상한까지 간 문항도 있었다(E029, E060).
- 목록과 본문이 어긋나는 문항이 16 → 32로 늘었다. 인기 게임 풀에는 같은 시리즈가 많다
  (Half-Life·Half-Life 2, Portal·Portal 2, GTA V·IV·San Andreas).

서버가 후보 전체를 조회하게 하자(3) 단계 실패가 사라지고 이름 누락도 18문항으로 돌아왔다. id 30개를
출력하지 않아도 되니 지연도 줄었다(11.15 → 10.72초). **고전 게임 풀에서는 id가 1~30이라 드러나지 않던
결함이다.**

### 읽을 점

- **이름 되묻기의 효과가 가장 크다.** 발견 2(목록과 본문의 이름 불일치)는 첫 실측부터 가장 큰 형식
  결함이었다. 16~18문항이 2문항이 됐고, 답변 형식 통과가 77~78 → 94다. 되묻기는 LLM 턴을 하나 더 쓰지만
  다섯 문항 중 하나꼴로만 걸려 지연 중앙값은 늘지 않았다(평균 +0.5초, p90 15.2 → 16.6초).
- **추천이 질문마다 달라졌다.** 한 시리즈로 채운 목록이 58/71 → 4/75다. 다만 "Portal 2"가 추천을 낸
  82문항 중 52문항에 들어간다(전에는 Thief II가 78문항 중 50문항). 검색 조건이 없는 질문이 많고
  Portal 2는 싸고 평가가 많아 어떤 조건에서도 살아남는다. 같은 게임이 자주 나오는 문제는 정렬로도
  선택 규칙으로도 풀리지 않았다.
- **추천 카드에 빈칸이 없어졌다.** 추천 문항당 경고(가격·리뷰 확인 불가)가 0.82 → 0.13이다.
- **예산 질문은 걱정과 달리 나빠지지 않았다.** 인기 게임은 비싸지만(상위 10개 중 3만 원 이하 93% → 56%)
  후보 30개를 다 조회하므로 20문항 모두 추천을 냈다. 아주 낮은 예산(`tight`)과 무료 강제(`free`)는
  전과 같이 거의 빈 추천이다.
- **심판 점수가 오른 것은 선택 기준(2) 이후다.** 취향에 맞춰 고르면서 답변이 조건과 이유를 더 잘 잇는다.

### 남은 위반 8문항과 오류 1건

- 제외 장르 2문항(E058, E060)은 에이전트가 아니라 **질문 분해의 오류**다. "공포 빼고"를
  `excluded_genres=["Horror"]`가 아니라 `genres=["Horror"]`로 뽑아 공포 게임을 검색한다. E058은 확인한
  여덟 번의 실행 모두에서 그랬다. **발견 3은 이것을 에이전트가 `excluded_genres`를 넘기지 않은 것으로 잘못 읽었다.**
- 사양 `skipped` 1문항(E081)은 발견 4 그대로다.
- 문장 수 3문항, 이름 누락 2문항.
- 오류 1건(E095, "혼자 할 3만 원 이하 스토리 중심 게임 1개만")은 `summarize_reviews`를 8번 반복 호출하다
  반복 상한에 걸렸다. 마지막 두 실행에서 연달아 났다. 프롬프트의 "at most once"는 지켜지지 않는다.
  Tool별 호출 횟수를 코드로 제한하고, 초안 없이 루프가 끝나면 통과 후보로 응답을 만드는 폴백이 다음에
  볼 자리다. 이날 반복 상한 오류는 실행마다 0~2건이었다.

- E058·E060·E091이 모두 `genres=[]`, `excluded_genres=["Horror"]`로 뽑혔다. E056은 Horror가 양쪽에 다

- 오류 1건은 또 E095다. `summarize_reviews`를 8번 반복 호출하다 반복 상한에 걸렸고, 세 번의 실행에서
  연달아 같은 문항이다. Tool별 호출 횟수 제한이 필요하다.

## Tool별 호출 상한 (2026-09-20)

위 절의 오류 E095를 고쳤다. 같은 Tool을 되풀이해 부르다 반복 상한(`recursion_limit=20`, Tool 턴 9번)에
걸리면 502로 끝난다. 프롬프트에는 "Call summarize_reviews at most once" 같은 문장이 Tool마다 있지만
코드로 막는 곳은 없었다.

### 상한을 정한 근거

지금과 같은 동작(가격·사양이 후보 전체를 조회)으로 돌린 세 실행 300건에서, `조건 판정` 전에 시작된
Tool 단계를 세었다.

| Tool | 0회 | 1회 | 2회 이상 |
| --- | --- | --- | --- |
| `search_games` | 0 | 300 | 0 |
| `get_prices` | 2 | 298 | 0 |
| `assess_hardware` | 2 | 298 | 0 |
| `get_review_scores` | 294 | 6 | 0 |
| `summarize_reviews` | 138 | 159 | 3 (모두 E095, 8회씩) |

정상으로 끝난 297건은 어떤 Tool도 두 번 부르지 않았다. E095를 직접 돌려 인자를 보면 반복은 같은 호출의
재시도가 아니다. 통과 후보의 리뷰를 **한 게임씩** 읽어 나간다.

```text
summarize_reviews([72]) → ([472]) → ([71]) → ([20]) → ([127]) → ([231]) → ([73]) → ([16]) → GraphRecursionError
```

호출마다 `igdb_ids`가 달라 "같은 인자면 막는다"로는 잡히지 않는다. 그래서 횟수를 센다.

- `search_games`·`get_prices`·`assess_hardware`는 **1회**. 다시 불러도 결과가 같다.
- `get_review_scores`·`summarize_reviews`는 **2회**. 모델이 id를 넘기므로, 후보에 없는 id로 거부된 뒤
  고쳐 부르는 한 번은 남겨 둔다. 아래 실행의 E058이 그 경우다(첫 호출은 없는 id로 즉시 실패, 두 번째
  호출이 성공).

### 집행

`app/agent/limits.py`의 `ToolCallLimiter`(LangChain 미들웨어)가 두 겹으로 막는다. 상한을 넘긴 호출은
Tool을 실행하지 않고 안내 문장을 돌려주고, 한 번 거부된 Tool은 다음 모델 호출부터 Tool 목록에서 뺀다.
상한에 닿기만 한 Tool은 빼지 않는다. 정상 흐름에서 모델이 받는 입력(Tool 목록, 메시지 순서)은 수정
전과 같다.

### 측정

| E095 | 실행 | 502 | 반복이 시작된 실행 |
| --- | --- | --- | --- |
| 수정 전 | 평가 3회 + 직접 5회 | 4 (평가 3, 직접 1) | 4 |
| 수정 후 | 직접 8회 + 평가 1회 | **0** | 4 (모두 세 번째 호출이 거부된 뒤 바로 초안 제출) |

수정 후 반복이 시작된 4회는 모두 `summarize_reviews`의 세 번째 호출에서 끊겼다(수정 전에는 8번 실행).
모델은 네 번 모두 안내를 받고 다음 턴에 초안을 냈으므로, Tool을 목록에서 빼는 두 번째 겹은 이 측정에서
쓰이지 않았다. 모델이 안내를 무시하는 경우를 위한 장치이고, 동작은 `tests/agent/test_limits.py`가 본다.

100문항(`20260919T171421Z`)

| | 수정 전 (`20260919T161404Z`) | 수정 후 |
| --- | --- | --- |
| 오류(502) | 1 (E095) | **0** |
| 세 축 모두 통과 | 94/99 | 91/100 |
| 조건 · 궤적 · 답변 형식 | 98 · 99 · 95 | 99 · 98 · 94 |
| 거부된 호출이 있었던 문항 | - | 0 |
| 추천 0개 (통과 후보가 있었던 것) | 17 (0) | 17 (0) |
| 지연 중앙값 | 10.67초 | 10.57초 |

- 이 실행에서는 상한이 한 번도 걸리지 않았다(E095도 이번에는 반복하지 않았다). 거부가 없으면 모델이 받는
  입력이 수정 전과 같으므로, 통과 수의 차이(94 → 91)는 상한과 무관하다. 내려간 쪽은 이름 누락이다(2 → 5문항,
  `더 위쳐 3: 와일드 헌트`처럼 번역한 이름을 되물은 뒤에도 그대로 냈다). 되묻기 뒤에도 남는 비율은
  실행마다 이 정도로 흔들린다.
- 궤적 위반 2건은 `리뷰 요약` 단계 실패다. E058은 없는 id를 넘겼다가 고쳐 불렀고, E086은 리뷰 요약이
  30초 시간 제한에 걸렸다(모델은 다시 부르지 않았고 러너가 확정 뒤에 채웠다).
- 지금과 같은 동작으로 돌린 앞의 세 실행(`20260919T143315Z`·`144436Z`·`161404Z`)은 모두 오류가 E095
  1건이었다. 한 번의 실행으로 "오류가 없어졌다"고 말할 수는 없고, 근거는 위의 E095 반복 실행이다.

## 전후 비교 갱신과 채점기 동기화 (2026-09-20)

2026-09-19 절의 "남은 것" 중 두 가지를 했다. 외부 API를 부른 것은 예상 질문 5개의 에이전트 재측정뿐이다
([evals/agent_questions/REPORT.md](../agent_questions/REPORT.md)).

### 채점기를 원본 저장소로 옮겼다

`score.py`·`run_eval.py`·`rescore.py`·`test_e2e_score.py`·`README.md`가 두 저장소에서 다시 같은 파일이다.
[rescore.py](rescore.py)는 답변 형식 축만 다시 계산했는데, "통과 후보가 있는데 추천이 0개"도 다시 보게
넓혔다. 이 검사는 단계 타임라인의 `조건 판정` detail과 추천 개수만 있으면 되기 때문이다. 조건 축의
나머지와 궤적 축은 여전히 기록된 판정을 쓴다.

원본 기록 `20260917T075948Z`를 다시 채점하면 기존 수치는 하나도 바뀌지 않는다(통과 후보가 있었던 빈 추천
0건). 새로 나온 것은 추천을 낸 문항만의 수치다.
